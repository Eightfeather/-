## 1. 分类重命名

调色板分类 `cond: '条件'` → **`cond: 'IF'`**，内部三张同级卡片：

| 卡片 | 标签 | 编译产物 | 说明 |
| --- | --- | --- | --- |
| IF | IF | `IF(cond):…` | 条件成立才执行下方积木 |
| IFNOT | IFNOT | `IFNOT(cond):…` | 条件不成立才执行（引擎 :2648） |
| CONTINUEIF | CONTINUEIF | `CONTINUEIF(cond)` | 条件不成立时**停止本行后续语句**；本行有遍历则**跳到下一次遍历**（文档 :3438-3444） |

（STOPIF 暂不做；LUA 段本次不做。）

## 2. IF 卡片改版：两行式头部 + 逻辑符

修复现状：`.bk-if-head` 是单行 flex，`label + 两个值槽 + 运算符 + 标签` 在窄画布下换行错乱、溢出。

```
┌ 如果 ───────────────────────────── IF ┐
│ [VALUE_0 ▾] [ > ▾] [ 5 ]      [无 ▾] │   ← 条件行 1
│ [VALUE_1 ▾] [ < ▾] [ 10 ]   [+ 条件] │   ← 条件行 2（仅 AND/OR/XOR 时出现，可删）
│ ⓘ 所有条件都成立才执行下方积木          │   ← 选中逻辑符后出现的一句解释
├───────────────────────────────────────┤
│  (body：拖效果函数到这里)              │
└───────────────────────────────────────┘
```

- 逻辑下拉四项：`无 / AND / OR / XOR`；选非「无」后出现「+ 条件」按钮与解释行。
- 解释文案：
  - 无：「只判断这一个条件」；
  - AND：「所有条件都成立，才执行下方积木」；
  - OR：「任意一个条件成立，就执行下方积木」；
  - XOR：「**恰好一个**条件成立才执行（两个都成立反而不执行）」。
- 条件上限 8 组（引擎无上限，UI 限 8 以保证可读）。
- 编译：`无` → `IF(VALUE_0>5)`；`AND` → `IF(AND,VALUE_0>5,VALUE_1<10)`；`OR`/`XOR` 同理（文档 :3457-3465）。
- 数据结构：`{ k:'if', logic:'none|and|or|xor', conds:[{left,op,right}], body:[] }`；旧数据 `{left,op,right}` 读入时自动转成 `conds:[…]`、`logic:'none'`，不破坏历史脚本。

## 4. 循环：移到时点右侧（横向槽），不再做缩进容器

```
  ╭─────────────╮   ╭──────────────────────╮
  │ ⚑ 使用时     │   │ ↻ 遍历：所有敌方  ▾   │   ← 行头右侧专用槽
  ╰─────────────╯   ╰──────────────────────╯
  ┌───────────────────────────────────────┐
  │ [buff(Self, 燃烧, 2)]                 │
  │ [如果 VALUE_0 > 3] → [healhp(Self,2)] │
  └───────────────────────────────────────┘
        ↑ 所有 Target 会被逐个替换成「所有敌方」，Self 不受影响
```

- 拖环形积木时，只有落点是「行头的 loop 槽」才接受；落别处 toast「遍历块只能放在时点右侧」。
- 每个时点行最多 1 个 loop；已有则替换（并 toast「已替换本行遍历目标」）。
- 悬停/选中 loop 槽显示语义提示：**「本行整段脚本的 Target 会被逐个替换（引擎 LOOP 是整条脚本级，不是块级）」**。
- 这样视觉与引擎一致：`/TIMING:X/LOOP:EveryEnemy/<body>/`。

## 6. 交互细节

- IF 条件行的值槽沿用现有类型系统（`num`/`var`/`acq`/`math`）；运算符仍只允许 `< > =`（引擎 :1695-1717 仅这三种）。
- CONTINUEIF 无 body，拖进画布后为单行积木；其后语句保持同级。
- IF/IFNOT 的 body 保持「拖效果函数进来」。

## 7. 待你拍板的一个问题（与本次设计相关）

引擎里 `IF` 是「**门控本批后续语句**」：同层 IF 之后的兄弟积木也会被它控制（`ProcessBatch:2655-2661` 遇到假条件直接 `break`）。现在画布把它们画成同级，容易被误读。三选一：

1. 保持现状，只加提示（改动最小）；
2. IF 之后的兄弟积木自动吸入 IF body（视觉=执行，但会改变用户摆放结果）；
3. 编译时把每个顶层语句拆成独立批次（`/IF(…):子句/`、`/效果/` 分开），视觉边界=执行边界（最贴合直觉，但要改编译与「一行」概念）。

## 8. 补充：STOPIF / CONTINUEIF 的真实语义（引擎实证）

`ModularSkillScripts.decompiled.cs` 执行主循环（:1567-1582）：

```csharp
while (enumerator2.MoveNext()) {          // 遍历 LOOP 目标（无 LOOP 时只有一个目标）
  modsa_loopTarget = current2;
  _fullStop = false;                      // ← 每个目标重置
  for (int i = 0; i < batch_list.Count; i++) {
    if (_fullStop) break;                 // ← 只中断「本目标的剩余批次」
    ProcessBatch(batch_list[i]);
  }
}
```

`ProcessBatch`（:2632-2647）：

```csharp
if (text.StartsWith("CONTINUEIFNOT")) { if (CheckIF(text)) { _fullStop = true; break; } }
else if (text.StartsWith("STOPIF") || text.StartsWith("CONTINUEIF")) {
  if (!CheckIF(text)) { _fullStop = true; break; }   // ← 条件为假才停
}
```

结论：
- **STOPIF(cond)**：条件**为假**时跳过「本目标」剩余的所有批次；进入下一个 LOOP 目标时 `_fullStop` 会被重置，所以**不会**杀掉整个脚本。
- **CONTINUEIF**：与 STOPIF 在安装版 DLL 里是**同一分支（完全等价）**；文档 :3438-3444 的描述（无 LOOP 时停其余脚本、有 LOOP 时跳到下一轮）与实现一致。
- **CONTINUEIFNOT**：反过来——条件**为真**才停（引擎支持，文档未写）。
- 对比 `IF/IFNOT`：它们只 `break` 当前批次（`ProcessBatch` 内），不影响其它批次。

## 9. 编译规则修正（采纳「用 / 分隔，IF 只管自己那段」）

既然 `IF` 的影响范围止于**本批次**，而 `:` 是同一批次内的语句分隔、`/` 是批次分隔，那么「视觉边界 = 执行边界」的正确写法是：

```
每行 = TIMING 段 ／ LOOP 段（可选） ／ 顶层语句各成一段
     （IF/IFNOT 连同其 body 合为「一段」，段内子句用 ':' 连接）
```

示例（同一时点下：两个无条件效果 + 一个条件块 + 一个循环内条件块）：

```
Modular/TIMING:WhenUse/buff(Self,Combustion,2)/IF(VALUE_0>3):healhp(Self,2)/gainshield(Self,5)
```

- `buff(Self,…)`、`IF(…):healhp(…)`、`gainshield(Self,5)` 是三个独立批次：IF 假时只跳过它自己那段；
- `LOOP:` 仍是模块级、作用于全部批次（文档 :63-67）；
- IF 的 body 不允许再见顶层兄弟被误吸；子句顺序保持 `IF(cond):子句1:子句2`。
