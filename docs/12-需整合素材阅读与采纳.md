## 2. `script-effects.json` 的原理

**它是什么**：游戏**原生脚本**（`Assembly-CSharp` 的 ScriptableObject）的效果对照表，不是 Modular 控件表（后者见 `src/knowledge/modular-tables.mjs`，226 条）。

**每条结构**（以 `GiveBuffOnSucceedAttack` 为例）：

```json
{
  "name": "GiveBuffOnSucceedAttack",
  "uses": 9036, "skillCount": 3211, "parameterless": false,
  "timing": { "id": "OnSucceedAttack", "zh": "[命中时]" },
  "effect": "[命中时] 使{target}增加 {stack} 级 [{buffKeyword}] 强度，并获得 {turn} 层 [{buffKeyword}]。",
  "effectSource": "curated", "confidence": "verified",
  "effectExample": "[命中时] 使目标增加5级[流血]强度",
  "params": { "buffData.stack": "【已统计验证】强度增加量…2402 例相符 / 66 例不符（约 97%）", "buffData.turn": "…层数增加量。注意：它**不是**持续回合数——与\"N回合\"相符 0 例" },
  "evidence": [ { "skillId": 107901, "skillName": "摧垮", "where": "coin", "text": "[OnSucceedAttack] 使目标增加5级[Laceration]强度", "zh": "[命中时] 使目标增加5级[流血]强度" } ],
  "sample": { "scriptName": "GiveBuffOnSucceedAttack", "buffData": { "buffKeyword": "Laceration", "target": "Target", "stack": 5, "turn": 0, "activeRound": 0 } }
}
```

**四条生成法则**（见 `meta.rules`）：
1. 无参脚本 → 直接采用所在位置的官方汉化文本（`evidence`）；
2. 有参脚本 → 带占位符的模板 + 一条 `effectExample`；
3. **会变的字段一律留占位符**（判据：该字段在全部实例里 `distinct === 1`）；
4. 行级归因打分（时点 / buff 关键词 / 数值 / 名字 token）挑出属于该脚本的那一行；内部标签已译成游戏显示用中文（`[OnSucceedAttack] → [命中时]`）。

**质量分布**（新版）：`verified 1896 / high 882 / medium 734 / low 425`；来源 `curated 2614 / special 46 / evidence 760 / literal 259 / composed 100 / idOnly 158`。
> `low` 的 425 条（多为 `idOnly` 编号命名与 `literal` 硬译）**不得作为权威展示**，UI 上必须标注。

## 3. 与 `D:\下载\效果总文本.json` 的关系（不是同一类东西）

- 该文件是 **UTF-16 LE + BOM**（直接 `JSON.parse` 会失败，需按 `utf16le` 解码），1.54 MB。
- 内容：`{"list":[{ id, iconId, buffClass, buffType, canBeDespelled, list:[{ability, value, buffData:{...}}], categoryKeywordList, ... }]}`
  → 这是**原版 Buff 的实体定义表**（1,664 个 buff，其中 1,441 个带 `list` 效果行），`list[].ability` 正是 §2 那些**脚本名**。
- 与 `script-effects` 的交集只有 **3** 个（因为一个是 buff id、一个是脚本名，本就不同域）。
- 与本地 `dumpedData/limbus_locale/EN/bufList.json`：1,664 个 id 里 **1,648 个能对上**；16 个对不上的是 `MRR546P`/`MRR546E` 这类（疑似后续版本新增）。
- **结论**：两者是**互补**关系 —— `效果总文本.json`＝「Buff 有哪些、每个 Buff 挂了哪些能力脚本」，`script-effects.json`＝「每个能力脚本具体干什么、参数怎么填」。前者适合做「Buff 效果一览/校验」，后者做「脚本→人话」。

## 5. 变体 vs 本地（0.6.7）：落地实操差异

### 5.1 端点（变体 68 / 本地 67 / 共有 64）

| 归属 | 端点 | 作用 |

### 5.2 关键差异：**装配与写回**

变体的 `POST /api/skill/save` → `saveCompiledSkill()`（`src/lethe/skills.mjs:256`）会：
1. 把模块里的 `scripts`（脚本对象数组）**展开进** `skillData[0].abilityScriptList` 与 `coinList[i].abilityScriptList`（`code.skill` / `code.coins[i].modules` 也支持）；
2. 处理红币/绿币（自动补 `SuperCoin`/`ExtractCoin`）、广域乱射（`isRandomAreaAttack` + `WideAreaRampageDealAllAtLastCoin`）；
3. 写回 `custom_limbus_data/skill/<rel>`（就地改实体）**与** locale（`levelList[].name/desc`、`coinlist[].coindescs`，中文用 `toGameText` 转成游戏标签）。
变体的被动 `requireIDList`、Buff `list[].ability` 同样从模块展开（`passives.mjs:238`、`buffs.mjs:267`）。

**本地 0.6.7**：模块只编译成 `Modular/...` 文本预览；`/api/skill/code` 写的是编辑器 meta，**没有把脚本写进游戏文件** —— 这是最大的能力缺口。
